# Chathistory: intermittent missing history + "unknown msgid" — investigation (2026-08-30)

**Status: Phase-1 root-cause investigation COMPLETE. No fixes applied yet — awaiting scope agreement.**
Worktree audited: `ircv3.2-hardening` @ `f0e6389`. Long-standing (predates the 2026-08 #103/#104 chains); reports concern messages **< 1 day old** on prod, so retention/eviction of old rows is not the story.

## Symptoms
(a) Messages delivered live are missing from replay / CHATHISTORY.
(b) A client holds a msgid (received on the wire) that the server's history disclaims — seen as `FAIL PERSISTENCE CURSOR_UNKNOWN` (attach-cursor resolution, `replay.c:817-831`) or empty msgid-anchored batches.

## Root-cause findings, ranked for prod (single fork server on AfterNET, `CHATHISTORY_REQUIRE_AUTH=1` per `ircd_features.c:1277` comment)

1. **F3 — auth-gate storage hole (LIVE ON PROD, by design but symptom-producing).** `ircd_relay.c:257-260`, `channel.c:126-129`: with REQUIRE_AUTH, a non-+H channel with `authusers==0` **delivers msgids but stores nothing**. Authed membership fluctuates → intermittent per-channel gaps; anchors from those windows unknown forever. Note the +Y/opt-out paths do it right (GAP marker keeps the msgid resolvable, `ircd_relay.c:264,417,424`) — the auth gate could store a GAP row instead of nothing.
2. **F4 — TAGMSG never stored: DMs unconditionally (`m_tagmsg.c:305-345,437-464` — no store call exists), channels gated on `FEAT_CAP_draft_event_playback` (default 0, `ircd_features.c:1207`).** Reactions/replies delivered with msgids the index never learns. If a client's newest-seen msgid is a reaction, its ATTACH cursor is unresolvable → CURSOR_UNKNOWN every reattach.
3. **F2 — multiline DM stored under the wrong key (unconditional bug).** `m_batch.c:1672-1674, 2470-2472` store with `target = cli_name(acptr)` (recipient nick) while every PM query path uses the sorted identity pair-key (`normalize_pm_target`, `m_chathistory.c:1040-1090`; `replay.c:65-77` requires a colon). Every multiline DM is delivered with `batch_base_msgid` but unreachable by any query; msgid→timestamp still resolves (index row written) but the anchored query lands in the wrong target. Also bypasses `should_store_pm` entirely (no opt-out / CHATHISTORY_PRIVATE / both-unauthed / STORE gates) — a privacy over-store in the other direction.
4. **Future read-marker poisoning (replay-side, my finding).** MARKREAD accepts any client timestamp, no clamp vs CurrentTime (`m_markread.c parse_timestamp_param`); `metadata_readmarker_set` is only-update-if-newer (`metadata.c:664+`) so a skewed-ahead device plants a marker that can never be lowered; both replay paths skip messages ≤ marker (`replay.c:381-385`, `m_chathistory.c:4210-4217`). Per-channel, device-dependent, self-healing when wall-time catches up → classic "intermittent missing history". (Multi-device marker skip — read on desktop ⇒ not replayed on phone — is the by-design cousin.)
5. **F1 — PM msgid misses are terminal.** `should_federate` refuses non-channel targets (`m_chathistory.c:1227-1231`), CH Q server side too (`:4620-4625`); all msgid-ref resolutions return empty on local-index miss. Any PM producer gap (F2, F4-DM, F5, retention) is unrecoverable.
6. **F6 — remote channel events (KICK/TOPIC/QUIT/NICK/JOIN/PART/MODE) stored only at origin** (all `MyUser(source)`-gated) while receivers deliver the propagated msgid. Also `derive_channel_msgid()` is dead code — multi-channel QUIT/NICK share one msgid, index row last-writer-wins across channels (`history.c:1075`), breaking AROUND inclusion for all but one channel.
7. **F10 — per-hop msgid re-mint without S2S tags** (`ircd_relay.c:854,949,1632,1741`; `FEAT_P10_MESSAGE_TAGS` default 0): each server self-consistent but cross-server divergent — bites bouncer reattach-via-other-server on multi-fork-server deployments (not prod today; will bite the mesh).
8. **F5 — BX E remote-session PM echo delivers msgid, no store** (`bouncer_session.c:6553-6590, 8529-8580`); with F1, terminal. Dormant on single-server prod.
9. **F7 — non-STORE topology holes**: CH W forward searches directly-linked peers only (`m_chathistory.c:2689-2705`); PMs on non-STORE servers neither stored nor forwarded; timestamp refs hard-fail before federation while msgid refs federate. Dormant on bed (both servers STORE) — live for mixed deployments.
10. **F8 — BETWEEN never federates** (`m_chathistory.c:1660-1714`).
11. **F12 — ephemeral PM ring ignores selectors** (only LATEST consults it).
12. **F13 — S2S channel store drops client tags** (`client_tags=NULL` at `ircd_relay.c:880,975`) → reply-context index only on origin server.

## Exonerated
Marker format mismatch (ISO→unix converted at parse); PM identity keying (account-anchored, F-CH1 honored); crash durability (RocksDB WAL buffered-write per commit — process crashes lose nothing; `sync_period_seconds` silently unwired on RocksDB backend, cosmetic); strict-presence (default off, logs `presence_filter_messages: … dropped=` when active); echo-message; multiline channel batches; local single-server PRIVMSG/NOTICE paths.

## Discriminators (prod log greps — instrumentation already exists)
- `history_msgid_to_timestamp: … NOT FOUND in cf_msgid index` (`history.c:2398`) — never-stored vs evicted split per incident.
- `presence_filter_messages: … kept= dropped=` — strict-presence involvement.
- Correlate a reported gap with channel authed-membership at the time (F3) and with the message type (reaction/multiline-DM → F4/F2).

## Proposed fixes (not yet agreed)
- F2: store multiline DMs under the identity pair-key via the `should_store_pm` gate path (bugfix, test-first).
- F3: store a GAP marker (msgid-indexed) instead of nothing in the authusers==0 window — mirrors the +Y pattern; anchors stay resolvable while content stays unstored.
- F4: store TAGMSG-DM (or at minimum index msgid→GAP); reconsider event_playback default for channel TAGMSG.
- Marker poisoning: clamp MARKREAD SET to `min(supplied, CurrentTime+ε)` at both m_markread and ms_markread ingress.
- F6: resurrect `derive_channel_msgid` per-channel for QUIT/NICK; store events at receivers or GAP-index them.
- F1/F8: allow msgid-ref federation fallback for PMs guarded by pair-key membership, or at least make PM msgid misses return FAIL rather than empty.

## Addendum 2026-08-30: legacy auto-mint verification (user hypothesis)
User design intent (stated 2026-08-30): **mint unconditionally whenever FEAT_MSGID is on; store subject to the standard gates** (initial formulation added "if there's local clients to see it", then corrected: "actually no, those should store").

Verified against code:
- **PRIVMSG/NOTICE channel + PM legacy relays are CLEAN.** parse.c:1756-1761 clears all S2S tag buffers per incoming server message (no stale-msgid collisions). `server_relay_channel_message` (ircd_relay.c:824-827 unified mint into the link buffer) and the PM ms paths (ircd_relay.c:1615-1680) mint ONCE under FEAT_MSGID and share the value across local delivery, alias fanout, store, and onward S2S. Delivered == stored msgid on a single server. Matches intent.
- **Where legacy auto-mint DOES violate the intent:** ms TAGMSG (store mints a msgid clients never saw, clients get none — m_tagmsg.c:169 fallback), event stores' fallback mints (F14: store_quit_events:268 etc. — stored msgid never on the wire), and events from legacy-server users not stored at all (MyUser gate, F6).
- **Cross-fork-server divergence (F10) is the historical legacy-auto-mint hazard:** the compact @A S2S tag does not traverse legacy ircu hubs, so two fork servers on a legacy network each mint independently for the same message. Dormant today (prod-test out of round-robin) but would produce exactly "client holds msgid the server disclaims" whenever clients move between fork servers — and may explain the older reports from when prod-test was in rotation. Any future second fork server on AfterNET reopens it.
- **Open intent question (not blocking):** store_channel_history's local-interest gate (ircd_relay.c:210-231) skips storing on servers with zero local members (hubs relaying). Near-moot for leaves (P10 doesn't route channel msgs to memberless servers), live for hubs (bed nef3). If "those should store" means hubs too, it's a one-line change but contradicts the in-code rationale comment. Held ghosts ARE MyConnect → hold windows keep storing (verified).
- authusers counter balance audit dispatched (REQUIRE_AUTH=1 on prod means any low-drift = intermittent storage hole; decrements are >0-guarded so underflow is masked) — results pending.

## Addendum 2 — 2026-08-30: authusers counter drift audit (CONFIRMED, spot-checked)
With REQUIRE_AUTH=1 (prod), `authusers` drifting low = channel storage silently stops even with authed members present; decrements are >0-guarded so drift is invisible; **sticky** until membership churn or channel destruction resets it; counter has ZERO test coverage. Six confirmed findings (all = FLAG_ACCOUNT changing between a member's add and remove, invalidating the re-evaluated guard):
1. `sasl_auth.c:617-625` — post-registration SASL SetAccount, no increment loop (reachable via services `SASL … D S` and async Keycloak completion post-CAP-END). Sequence: unauthed join → post-reg auth (uncounted) → any counted member parts → counter 0 with authed members present. **UNDER**
2. `m_register.c:236` — native /REGISTER attaches account to connected client, no increment; their later PART decrements a count they never added. LIVE ON PROD since account-registration shipped 2026-08-06. **UNDER**
3. `s_user.c:2396/2525-2549` — SVSMODE/server MODE +r stamp on live client; s_user.c has zero authusers refs. **UNDER**
4. `m_account.c:446` — legacy (EXTENDED_ACCOUNTS=0) AC branch lacks the increment loop its extended twin (:256-262) has. **UNDER**
5. `m_account.c:256-262` — AC M (account CHANGE) reaches unconditional ++ with user already counted; origin undercounts (via #1), every peer overcounts → permanent leak + cross-server disagreement. **OVER/leak**
6. `sasl_webhook.c:67-70` — webhook deauth decrement loop has no IsMemberAlias filter and handle_sessions_for_account matches bouncer aliases (never-counted memberships) → steals counts; can zero a channel with authed members. **UNDER** (`m_account.c:190-193` AC U same shape, SUSPECT — alias numeric reachability unproven; filter cheap regardless.)
Ruled out as CLEAN (verified with flags-argument extraction, not eyeballing): burst members (account arrives via NICK +r before BURST), zombies, kick/part/quit/netsplit, channel destruction, bouncer restore/promote/demote/BX P/BX C convert, all CHFL_ALIAS paths, relocate, all pre-registration account attaches.
Secondary (not counter bugs): `sasl_webhook.c:84` sends `AC U` without the EXTENDED_ACCOUNTS branch → legacy-config peers never clear the account; aliases keep FLAG_ACCOUNT after primary deauth (bounce_emit_alias_update bails on !IsAccount(primary) because ClearAccount runs first) — self-consistent but counter stops meaning "authed members"; fixing emit order alone would CREATE an imbalance — revisit promote/demote guards together.
**Fix shape (agreed-good candidate):** one `channel_account_adjust(cptr, delta)` helper walking memberships, skipping IsMemberAlias; called at the five transition points ('M' = −old then +new) and substituted for the two open-coded loops; CMocka case per transition (TDD — currently zero coverage).
