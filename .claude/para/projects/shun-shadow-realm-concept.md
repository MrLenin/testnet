# Shadow realm — a containment-based SHUN replacement (concept)

Sketched 2026-07-30. **Status: LARK — loosely scoped, unowned, not committed to.** Recorded so the
analysis survives; the idea only clears cost/benefit under one specific framing (containment, not
deterrence — see "The only framing that pays"). Read [[shun-detectability-wontfix]] first: stealth
hardening of SHUN is already ruled out, and this is *not* an attempt to relitigate that.

## The idea

Instead of dropping a shunned user's commands (SHUN today), drop the *user* into a virtual
environment: their commands work, their messages go somewhere, the server behaves normally — but
nothing they do reaches the real network.

## Three axes, three designs

SHUN moves one lever (outbound). Separating the axes shows the actual design space:

| | outbound escapes? | inbound real? | commands appear to work? |
|---|---|---|---|
| SHUN today | no | yes | **no** ← every leak traces here |
| **A. Shadow-mute** | no | yes | yes |
| **B. Shared honeypot cell** | to other shunned users only | shadow only | yes |
| **C. Personal virtual world** | no | fabricated | yes |

**A — shadow-mute.** The user sees the real channel at real volume; their own messages echo back;
they are simply never answered. The cheapest option and the most convincing, precisely because it is
the most ambiguous — being ignored on IRC is indistinguishable from being ignored on IRC. No content
generation, no fake world, no consistency problem for anyone else's state because none of it is
faked. (This is essentially the "preserved illusion" branch of [[shun-protocol-coherence]] taken to
its conclusion; it inherits the ~11-emit-site relay surgery that was priced and declined there.)

**B — shared honeypot cell (the version worth anything).** All shunned users land in the same shadow
space and see each other. The critical property: **the ambient activity that makes the cell look
alive is generated by the other occupants, for free.** Spammers spam each other. A personal cell has
the empty-room problem and needs synthesized traffic; a shared cell solves it with population. The
population being deceived — drones — is exactly the population with no priors about what the real
channel looks like, so the fake survives contact.

**C — personal virtual world.** Dies on content synthesis. The killing constraint is **prior
knowledge**: a regular who knows `#chan` runs 200 users and scrolls fast spots a quiet mirror in
seconds. Fabricating plausible per-channel traffic is an unbounded problem. Not worth pursuing.

## Primitives that already exist

Two load-bearing pieces are already in the tree, which is what makes B less absurd than it sounds:

- **`IsLocalChannel`** (`&`-prefix, `include/channel.h:177`) — channels that never propagate S2S.
  The suppression plumbing is already threaded through mode handling (`channel.c:2950` strips
  `MODEBUF_DEST_SERVER`).
- **`CHFL_DELAYED`** (delayed-join, `include/channel.h:84`, `RevealDelayedJoinIfNeeded`) — the
  codebase already maintains *divergent per-viewer membership views* of one channel as a tested,
  load-bearing concept. "The membership you see is not the true membership" is not new machinery.

So joining a shunned user to a non-propagating channel with a filtered membership view is composition
of existing mechanisms, not new invention.

## The tax: every state view has to lie consistently

The same tax that killed the stealth work, spread wider. NAMES, WHO, WHOIS, LIST, MODE, TOPIC,
WATCH/MONITOR, invite lists, away-notify, account-notify — each must present the shadow view to the
shunned and the real view to everyone else. **Every missed view is an oracle worse than the one
being closed.** This is the reason the idea is a lark and not a plan.

### Fork-specific hazards (each alone is disqualifying if unhandled)

- **chathistory** — a shunned user querying real channels sees real history minus their own
  messages; shadow-cell history must be stored (or synthesized) separately and must never be
  readable by real users. Per-viewer history filtering is the storage trap identified and rejected
  twice already.
- **crdt-mesh** — channel state replicates via the CRDT doc on that fork. Shadow state entering the
  doc is a divergence/resurrection hazard against the crdt-mesh skill's HARD INVARIANTS. Shadow
  channels must be structurally incapable of reaching `crdt_shadow` — `&`-locality helps, but it
  must be *proven*, not assumed, on that branch.
- **bouncer** — `bounce_send_channel_state` replays channel state on revive; session aliases must
  see consistent shadow state across reconnects and across servers, or the illusion breaks exactly
  when a real client reconnects. Shun-state must also survive (or deliberately not survive)
  hold/revive — either choice needs specifying.
- **services (X3)** — AuthServ/ChanServ interactions from inside the cell either work (leak vector:
  services see the user; MEMOSERV reaches real users) or fail (oracle). Services traffic must be
  scoped like everything else.

## The only framing that pays

As a **better SHUN**, this fails the maintainer's own test: SHUN is a soft deterrent for users who
don't know to check ([[shun-detectability-wontfix]]); anyone sophisticated enough to need a
honeypot-grade illusion is outside its threat model, and the consistency tax buys stealth nobody
asked for.

It becomes defensible only if the **goal changes from deterrence to containment**:

- **Absorption** — a drone run that lands in the cell stays busy and connected instead of detecting
  the block and rotating IPs/nicks. Wasting the operator's time is the product.
- **Observability** — the cell is a supervised space. What the drones do in there (spam payloads,
  URL rotation, C2 patterns, timing) is intelligence, collectable passively by opers watching a
  channel that costs nothing to watch.

That is a different product with different value, and it should be proposed (if ever) as that — an
oper containment/observation tool that happens to reuse shun matching — not as a SHUN improvement.

## The cheap probe, if interest ever materializes

One day, answers the riskiest question first: create an `&`-style non-propagating channel, place two
shunned test clients in it with a filtered membership view, and hammer NAMES / WHO / WHOIS / LIST /
MODE from both inside and outside. Either the composition of `IsLocalChannel` + `CHFL_DELAYED`-style
filtering holds up — validating the whole approach — or it leaks in the first hour and the idea dies
for the price of a spike instead of a subsystem. On `crdt-mesh`, the spike must additionally prove
the channel never appears in the CRDT doc.

## Verdict

Not proposed. B is the only viable variant; it pays only under the containment framing; and even
then it competes with "just Z-line them" on cost. Parked here so the axes table, the
existing-primitives observation, and the fork-specific hazard list don't have to be re-derived if
the containment use-case ever becomes real.
