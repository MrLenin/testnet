# SASL / Keycloak Skill

Reference for Nefarious's local SASL path (direct Keycloak auth via libkc) and its three-tier dispatch. For the P10 SASL relay wire format see `p10-protocol.md`; for libkc's event integration see `nefarious-codebase.md`.

## Local SASL (Keycloak Direct)

- `sasl_auth.c` / `sasl_auth.h` — local SASL PLAIN via a Keycloak ROPC grant through libkc.
- Three-tier dispatch in `m_authenticate.c`: **local Keycloak → IAuth → P10 relay**.
- `sasl_local_available()` checks `sasl_local_initialized && FEAT_SASL_LOCAL && kc_sasl_healthy`.
- Health tracking via `sasl_health_cb` — toggles CAP NEW/DEL for the `sasl` capability.
- libkc HTTP detail (lives in the external libkc library, not this repo): `CURLOPT_POSTFIELDSIZE` must be set **before** `CURLOPT_COPYPOSTFIELDS` (per curl docs). Not verifiable from the Nefarious tree.

## Mechanism Support

Which mechanisms get *advertised* is gated by `FEAT_SASL_LOCAL_MECHANISMS` (default `"PLAIN,OAUTHBEARER"`); the off-by-default handlers all exist in `sasl_auth.c`.

- **PLAIN** — SASL_LOCAL, iauthd-ts, and X3 relay. Advertised by default.
- **OAUTHBEARER** — SASL_LOCAL only. Advertised by default.
- **EXTERNAL** — SASL_LOCAL has a real handler (`sasl_handle_external`): matches the TLS client-cert fingerprint `cli_sslclifp()` against Keycloak's `x509_fingerprints` attribute. Also via X3 relay. iauthd-ts does NOT support it. Off by default.
- **SCRAM-SHA-256** — fully implemented in SASL_LOCAL (`sasl_scram_*`, HMAC-SHA256 ClientProof). Off by default.
- **ECDSA-NIST256P-CHALLENGE** — fully implemented in SASL_LOCAL (`sasl_handle_ecdsa`, challenge + `EVP_DigestVerify`). Off by default.

## Caches & Cross-Server Coherence

- **Phase 4a/4b** (committed): auth caches (SipHash-2-4 negative/positive), webhook handler with deauth via `AC U`.
- **Phase 4c** (committed to submodule): CI token for cross-server cache coherence.
- **Webhook**: a single *inbound* HTTP listener (`sasl_webhook_init(const struct kc_webhook_config *)` on top of libkc's `kc_webhook` server) receiving Keycloak events (password change / delete / disable / logout). Configured by a `Webhook {}` block (`port`, `secret`, `vhost`, `path`, the four limits, `signaturewindow` 300, `legacysecret` no, `realm` = the Keycloak block's realm by default); the `WEBHOOK_PORT` / `WEBHOOK_SECRET` features still work but log a deprecation warning at every rehash (the bed's confs use them). One port, no URL list, no outbound delivery.
- **Webhook transport (2026-09-23, plan 3)**: the SPI signs every delivery, `X-Webhook-Signature: t=<unix>,v1=<hex HMAC-SHA256(secret, "<t>." + body)>`, and puts `realmName` in every payload. `ircd/kc/kc_webhook_sig.c` (pure, cmocka) verifies within the window and keeps a 256-slot ring of event ids; `kc_webhook.c` answers 401 for missing / malformed / stale / mismatch / replay and 403 for another realm at HTTP time, counts each cause and calls the ircd's `on_reject` callback. A payload without `realmName` (an older SPI) is accepted and counted. `legacysecret = yes` accepts the plain `X-Webhook-Secret` header alone (deploy window only: SPI first, then ircd). The ring holds the ids the listener accepted with their newest signature `t` (user decision 2026-09-24): a copy signed no later than that is a replay (401); a copy the SPI signed again later is its own retry of an event already queued (its 200 was lost), answered 200 and not acted on again (`Duplicates` under STATS); an id the queue could not take (503) is forgotten so the retry is new. The realm check runs before the ring, so a refused foreign event takes no slot. **Plan 4 (2026-09-24): every ircd receives every event directly** (the SPI URL list names them all); a receiver purges its own caches, deauths ONLY the sessions it owns (`bounce_deauth_classify` SKIPs remote clients: `remote_ok` 0), and sends one `CI <names|*> <kc_id|*> <event_id> <kind>` relay carrying every name it resolved; an ircd-side applied-events log (`webhook_eventlog.c`, `WEBHOOK_EVENTLOG_SIZE` 1024) dedupes direct deliveries and relays by the event id; at end of burst `sasl_webhook_link_catchup` sends a new peer the last `WEBHOOK_EVENTLOG_WINDOW` (86400 s) as `CI ... B` lines, a superseded disable as a purge. KILL switches must match network-wide; deploy the chain together (an old server deauths nobody on a relay). A rehash that changes only the secret goes through `kc_webhook_set_secret` and keeps the listener and every counter; anything else re-inits (the handler's counters survive, libkc's listener counters are zeroed). A listener start that fails (busy port, bad `vhost`) leaves the ircd without a listener: it says so to every oper, `STATS webhook` reports NOT RUNNING, and the next rehash retries even with unchanged values. Surfaces: `STATS webhook` (oper: listener, events, refusals by cause, last refusal, handler counters) and a `SNO_UNAUTH` notice once per cause per 60 s. A payload `username` is used only if it can travel the wire (`username_usable` in `webhook_subject.c`: at most 32 bytes, no space, colon, control or DEL); otherwise the id alone resolves the subject.
- **Account timestamp on the wire (user rulings 2026-09-24):** the `ts` in `AC R|M <account> <ts> <id>` and `+r account:ts:id` is X3's registration date, stamped by X3 when it authenticates a user itself; X3's check refuses a stamp that differs from the date it knows (restored to its pre-a52968b form in x3 `feature/keycloak-identity`; "can't retire it yet", legacy servers still authenticate through X3). The fork sends `0` there on every local Keycloak login (nefarious `fix/no-ircd-account-timestamp`): Keycloak's creation time is the directory's date, not X3's. The SASL relay path (m_sasl.c) still carries X3's own stamp. The Keycloak id is the identity: a different id under a bound name RESETS the X3 handle (Rubin's rule) and the replaced id is remembered so old sessions (bursts, alias attaches, the ircd's 5-min SASL cache) bind instead of resetting again.
- **OAUTHBEARER validation (2026-09-24):** local JWKS validation first (no credential); `kc_url_introspect` now builds `.../openid-connect/token/introspect` (the bare `/introspect` answered 405 with a JSON body libkc read as `active=false`, so the fallback had never worked; nefarious `fix/oauthbearer-introspection`); a `KC_FORBIDDEN` local verdict (not a JWT, bad signature, expired) answers ERR_SASLFAIL at once and is not introspected. Nothing revokes an accepted token before `exp` except the fallback; Rubin accepts tokens-valid-until-expiry, Keycloak policy owns lifespans.
- **CI token**: `CACHEINVAL` / `CI` — a P10 token, silently ignored by legacy servers. Handled by `ms_cacheinval()` in `sasl_webhook.c`.
- **CI id form (2026-09-23, plan 2 of the webhook audit)**: `CI <username|*> [<kc_id>]`. The positive cache entries carry the compact Keycloak id since step 5, so a delete or admin reset -- which Keycloak names only by uuid -- purges by id (`sasl_cache_invalidate_id`) here and on every fork server; `*` = no name. Old receivers ignore the second parameter and find nothing under `*`. Sender: `cache_invalidate_subject()` in `sasl_webhook.c`.
- **Webhook subject by id**: `USER` admin events carry no username (delete, reset-password: only `resourcePath: users/<uuid>`; update: the changed fields, `enabled` among them when it changed). `include/webhook_subject.h` (pure, cmocka over real fixtures under `ircd/test/fixtures/webhook/`) turns an event into (kind, compact id, payload name); the handler deauths under every account name the id resolves to and matches clients by id when both sides carry one. `authDetails` is the acting admin, never the subject (the parser no longer reads its username). Bed e2e: `tests/src/services/keycloak-webhook-e2e.test.ts` (real admin actions on a throwaway user).

## Transition Architecture

Read-only LDAP federation short-term (no X3 changes); Keycloak as authority long-term.

## Operational Notes

- Keycloak is **not** slow — test timeouts are usually test infrastructure, not Keycloak latency (avg ~45ms; rare ~1s outlier). Use generous timeouts (10s+ for SASL flows) and `retry: 2` for KC-dependent tests.
- Keycloak `PUT` requires the FULL user representation; omitted fields get cleared. GET → merge → PUT, and update the `kc_user_repr_cache` AFTER merging (not before). Strip `credentials` from cached reprs — including them in a PUT ADDS a credential rather than replacing, causing duplicate passwords.
- **Keycloak user id at login — take it from the ID token, not the access token.** On Keycloak 25+ an access token's `sub` comes from the `basic` client scope; the ircd's client is admin-capable (manages accounts, receives events) and may not carry it, so never read `sub` from the access token. Ask the password grant for `scope=openid` and read `sub` from the returned `id_token`: it is mandatory there and independent of client scopes (the `basic` `sub` mapper targets only the access token and introspection — confirmed on the bed 2026-09-23, Keycloak 26.4.7). The userinfo endpoint is the other non-admin source. General rule (user, 2026-09-23): the ircd relies on non-admin Keycloak paths whenever feasible.
- **Credential scoping (direction, 2026-09-23):** the ircd's login paths (PLAIN, OAUTHBEARER) need no Keycloak role; only EXTERNAL, SCRAM/ECDSA and /REGISTER use the admin API, and the bed's service account holds `realm-admin` (`scripts/setup-keycloak.sh`). Decided direction: certificate login becomes a certfp grant type in the SPI jar (Keycloak `OAuth2GrantTypeFactory`), libkc gets a login pair and an admin pair; SCRAM/ECDSA are undecided (SPI lookup endpoint or retire). Measured minimum roles: query-users (EXTERNAL only), view-users (SCRAM/ECDSA), manage-users (/REGISTER); the bed holds manage-users. Design: `.claude/para/projects/keycloak-certfp-grant-and-credential-scoping-2026-09.md`. Do not add ircd paths that need `view-users`/`manage-users`.
- **Async race on concurrent user updates**: when two async ops update the same user (e.g. email + attribute), the second op can read a cache populated by the first op's GET before the first op's PUT lands — its merge is against stale state, and its PUT overwrites the first op's changes. Mitigation: update the cache **immediately after merging** your changes (so the next op sees the new state), not after the PUT returns.
